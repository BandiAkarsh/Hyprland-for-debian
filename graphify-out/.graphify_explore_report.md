## 2. Per-Module Analysis

### src/config/ -- Configuration Systems (3 subsystems)

**Purpose:** Configuration parsing, value storage, and action dispatch. The most architecturally interesting module because it has THREE parallel implementations.

#### 2a. Shared Layer (`config/shared/`)

**Key abstractions:**
- `IConfigManager` (interface) -- abstract base for both config backends
- `Config::Actions::` namespace -- centralized action dispatch (the `ConfigActions.cpp` god file)
- `ActionResult` -- `std::expected<SActionResult, SActionError>` as the universal return type
- `CActionState` -- singleton holding global keyboard state (`m_passPressed`, `m_lastCode`, etc.)
- `SConfigError` / `ErrorResult` -- typed error system with levels (SILENT/INFO/WARNING/ERROR) and codes
- `CConfigValue<T>` -- template-based config value accessor (reads via `Config::mgr()->getConfigValue()`)
- `ConfigErrors.hpp` -- `configError()` factory function, which is the base for `actionError()`

**Design rationale:**
- The shared layer decouples config parsing from action execution. Any config system (legacy or Lua) populates the same config values, and both call into `Config::Actions::*` functions.
- `std::expected` is used throughout as a monadic error channel -- actions return either `SActionResult` or `SActionError`.

**Key entry points:**
- Every function in `ConfigActions.hpp` (~50+ action functions) -- these are the "single source of truth" for all window management operations.

**Notable patterns:**
- **Strategy pattern** via `IConfigManager` interface (both legacy hyprlang and Lua implement it)
- **std::expected monad** for error propagation
- **Singleton** via `Config::mgr()` returning global `UP<IConfigManager>`

#### 2b. Legacy Config System (`config/legacy/`)

**Key files:**
- `ConfigManager.hpp/cpp` -- hyprlang-based config manager
- `DispatcherTranslator.hpp/cpp` -- string-to-dispatcher mapping (the `wrap()` hub)

**Key abstractions:**
- `Legacy::CConfigManager` implements `IConfigManager` via `Hyprlang::CConfig`
- `CDispatcherTranslator` -- map of string -> function (`m_dispMap`) with 70+ entries
- `SDispatchResult` -- simple struct `{passEvent, success, error}`
- **`wrap()` helper (degree 65)** -- converts `ActionResult` -> `SDispatchResult`:
  ```cpp
  static SDispatchResult wrap(ActionResult res) {
      if (!res) return {.success = false, .error = res.error().message};
      return {.passEvent = res->passEvent};
  }
  ```
  This bridges the "old" `SDispatchResult` world (hyprlang dispatchers) with the "new" `ActionResult` world (shared actions). Every static dispatcher function in DispatcherTranslator.cpp calls `wrap(Actions::someAction(...))`.

**How dispatch works:**
1. Hyprlang parses a `bind` statement -> calls `handleBind()`
2. `handleBind()` registers the dispatcher name + arg in `SKeybind`
3. On keypress, `CKeybindManager::handleKeybinds()` looks up the keybind
4. Calls `Legacy::translator()->run(handler, arg)`
5. `run()` looks up `m_dispMap[handler]` and calls the registered function
6. The function calls `wrap(Actions::someAction(...))` which translates to `ActionResult`

**Notable:** The translator constructor (lines 788-859) is a massive initializer list registering all ~70 dispatcher names as lambdas/function pointers. Each dispatcher is a thin shim that validates args then delegates to `Actions::*`.

#### 2c. Lua Config System (`config/lua/`)

**Key files:**
- `ConfigManager.hpp/cpp` -- Lua-based config manager implementing `IConfigManager`
- `LuaBindings*.cpp` -- 9 files registering Lua API functions
- `objects/` -- 12 Lua object wrappers (`LuaWindow`, `LuaWorkspace`, etc.)
- `types/` -- 12 Lua config value types (`LuaConfigInt`, `LuaConfigColor`, etc.)
- `bindings/` -- Dispatchers, config rules, queries

**Key abstractions:**
- `Lua::CConfigManager` implements `IConfigManager` via embedded `lua_State*`
- `ILuaConfigValue` -- abstract config value type
- `CLuaEventHandler` -- Lua event callback system
- `SLuaTimer` -- Lua-managed timers
- Watchdog system (`watchdogHook`) -- prevents runaway Lua code:
  - `LUA_TIMEOUT_CONFIG_RELOAD_MS = 1500`
  - `LUA_TIMEOUT_KEYBIND_CALLBACK_MS = 100`
  - `LUA_TIMEOUT_EVENT_CALLBACK_MS = 50`

**Design rationale:**
- Embedded Lua with a **watchdog instruction counter** (every 10k instructions) to prevent hangs
- Timeout-per-operation granularity (different timeouts for config reload vs keybind callbacks)
- Lua config values are registered via `registerValue()` which creates metatable-based objects
- The binding system wraps Hyprland objects (Window, Workspace, Monitor) as Lua userdata with metatables

**Key entry points:**
- `Lua::CConfigManager::init()` -- loads and executes the Lua config file
- `LuaBindingsRegistration.cpp` -- registers all Lua API functions
- `LuaBindingsDispatchers.cpp` -- Lua dispatchers (can be triggered by keybinds, event callbacks, etc.)

#### 2d. Config Type System (`config/values/`)

- `ConfigValues.cpp/hpp` -- auto-generated config value definitions
- `types/IValue.hpp` -- base interface for typed config values
- **Relationship:** Both legacy and Lua config systems register values through `IConfigManager::registerPluginValue()` and `getConfigValue()`.

### src/protocols/ -- Wayland Protocol Implementations

**Purpose:** Implement ~60+ Wayland protocol extensions (the wlr-protocols, KDE protocols, Hyprland-specific protocols).

**Key abstractions:**
- Each protocol gets a pair of files: `FooProtocol.cpp/hpp`
- Many share a common pattern: `CWLFooResource`, `CFooProtocol`, `bindManager()`, `destroyResource()`
- `core/` subdirectory for core Wayland protocols (compositor, subcompositor, data-device, etc.)
- `types/` subdirectory for shared protocol types

**Design rationale:**
- Each protocol is self-contained with its own resource class
- The `ProtocolManager` creates and manages all protocol instances
- Protocols follow the Wayland pattern of `wl_global` + `wl_resource`:
  - `bindManager()` -- creates a global for the protocol
  - `destroyResource()` -- cleanup on client disconnect

**Notable patterns:**
- **RAII for wl_resources** -- C++ classes wrap wl_resource lifetimes
- **Signal-based event propagation** -- protocols emit signals that Compositor or managers subscribe to
- **Isolated state** -- each protocol manages its own state (offers, devices, etc.)

**Key protocols (representative):**
- `XDGShell` -- xdg_surface/xdg_toplevel lifecycle
- `LayerShell` -- layer shell surfaces (panels, notifications)
- `SessionLock` -- lockscreen protocol
- `Screencopy`, `ToplevelExport` -- screen capture
- `PointerConstraints`, `RelativePointer` -- pointer confinement
- `TextInputV1/V3`, `InputMethodV2` -- text input / IME
- `DragAndDrop` -- DnD via wlr-data-control protocol family
- `FractionalScale`, `TearingControl`, `DRMLease` -- display protocols
- `IdleNotify`, `IdleInhibit`, `ShortcutsInhibit` -- idle management

### src/render/ -- OpenGL Rendering Pipeline

**Purpose:** Compositing and rendering all graphical output.

**Key abstractions:**

**Renderer hierarchy:**
```
IHyprRenderer (interface)
  └── GL::CHyprGLRenderer (concrete, currently the only impl)
        └── CHyprOpenGLImpl (the actual GL state machine)
```

**Pass-based rendering:**
- `CRenderPass` -- ordered collection of `IPassElement` objects
- Each `IPassElement` draws one thing: border, shadow, surface, rect, texture, clear, framebuffer, hints, blur, inner glow, texture matte
- `CRenderPass::render()` iterates elements, handles occlusion, blur regions, debugging
- `pass/` directory has 13 pass element types

**Key rendering flow:**
1. `IHyprRenderer::renderMonitor()` is called per frame
2. Layers are arranged (background, bottom, overlay, top)
3. Windows are rendered via draw orders
4. Each window's decorations (shadow, border, glow) are rendered via `IHyprWindowDecoration` implementations
5. Pass elements are collected and sorted into `CRenderPass`
6. `CRenderPass::render()` executes the draw calls

**Decorations system:**
- `IHyprWindowDecoration` interface
- Implementations: `CHyprBorderDecoration`, `CHyprDropShadowDecoration`, `CHyprGroupBarDecoration`, `CHyprInnerGlowDecoration`
- `DecorationPositioner` computes positioning

**Notable patterns:**
- **Strategy pattern** -- `IHyprRenderer` abstract renderer, `IHyprWindowDecoration` for decorations
- **Command pattern** via pass elements -- each `IPassElement` encapsulates a drawing operation
- **Double/triple buffering** via `CGLFramebuffer` management
- **Lazy shader compilation** -- `CShader` created from source, reusable across frames

**Key abstractions:**

**State:**

**Rule system:**

**Notable patterns:**

- **Decorator** via `IHyprWindowDecoration` -- decorations layered on windows

### src/layout/ -- Tiling Algorithms

**Purpose:** Arrange windows within workspaces using various algorithms.

**Key abstractions:**

```
ITarget (layout-agnostic target)
  ├── CWindowTarget (single window)
  └── CWindowGroupTarget (window group)

CAlgorithm (composite: delegates to tiled + floating sub-algorithms)
  ├── ITiledAlgorithm (interface for tiling algos)
  │     ├── CMasterAlgorithm
  │     ├── CDwindleAlgorithm
  │     └── CScrollingAlgorithm
  └── IFloatingAlgorithm (interface for floating behavior)

CSpace (per-workspace layout space, owns one CAlgorithm per workspace)

CLayoutManager (global: manages all spaces, drag, resize)
```

**Algorithm hierarchy (IModeAlgorithm):**
```
IModeAlgorithm (base interface)
  ├── ITiledAlgorithm (tiling-specific interface)
  │     ├── CMasterAlgorithm -- master-stack layout (left/top/right/bottom/center)
  │     ├── CDwindleAlgorithm -- recursive binary-split layout (preserve_split, split ratios)
  │     ├── CScrollingAlgorithm -- column-based scrolling layout
  │     └── CMonocleAlgorithm -- full-screen tiling (one visible at a time)
  └── IFloatingAlgorithm (floating behavior)
```

**Design rationale:**
- **Template Method** via `IModeAlgorithm` -- each algorithm defines how targets are added, removed, moved, and resized
- **Composite** via `CAlgorithm` -- a workspace's algorithm = tiled algo + floating algo, managed as one unit
- **Target abstraction** -- layouts manipulate `ITarget`, not `CWindow` directly, enabling groups to be tiled as units

**Key entry points:**
- `CLayoutManager::newTarget()` -- adds a window/group to a workspace's layout
- `CLayoutManager::recalculateMonitor()` -- re-layouts a monitor's active workspace
- `CLayoutManager::layoutMsg()` -- forwards layout-specific messages (e.g., "cyclenext", "orientation left")
- `WorkspaceAlgoMatcher` -- maps workspace selectors to algorithm types

**Notable patterns:**
- **Strategy pattern** for layout algorithms (selectable per workspace)
- **Binary tree** in Dwindle algorithm (`SDwindleNodeData` with parent + 2 children)
- **Column-based** in Scrolling algorithm (`SColumnData` with ordered targets)

## 3. Key Design Decisions and Trade-offs

### Decision 1: Three Config Systems (Legacy + Lua + Shared)
**Why:** Migration path from hyprlang to Lua without breaking existing configs.
**How:**
- `IConfigManager` interface abstracts both
- `initConfigManager()` auto-detects `.lua` extension vs `.conf`
- Both systems populate the same `Config::Actions::*` functions
- **Trade-off:** Increased complexity in config dispatch (extra translation layer via `wrap()`) but clean migration path

### Decision 2: std::expected for Error Handling
**Why:** Monadic error handling avoids exceptions in the hot path and makes errors explicit in signatures.
**How:**
- `ActionResult = std::expected<SActionResult, SActionError>`
- `ErrorResult = std::expected<void, SConfigError>`
- `actionError()` and `configError()` factories return `std::unexpected`
- Warnings, infos, and errors all use the same type (differentiated by `eActionErrorLevel`)
- **Trade-off:** More verbose signatures, but compile-time checked error handling

### Decision 3: Target Abstraction (ITarget)
**Why:** Decouple layout algorithms from window management. Groups can be treated as tiling units.
**How:**
- `ITarget` has implementations: `CWindowTarget`, `CWindowGroupTarget`
- Layout algorithms operate on `ITarget`, not `CWindow`
- `CLayoutManager` mediates between window management and layout operations
- **Trade-off:** Extra indirection layer, but enables group tiling and future view types

### Decision 4: Pass-Based Rendering
**Why:** Decouple rendering passes from the GL state machine, enable future Vulkan backend.
**How:**
- `IPassElement` subclasses represent individual draw operations
- `CRenderPass` collects and sorts them, handles occlusion culling
- `IHyprRenderer` hides backend details behind an interface
- **Trade-off:** Slightly more overhead than direct GL calls, but enables clean backend abstraction

### Decision 5: Global Singleton Managers
**Why:** Ubiquitous access needed from all parts of the code (config actions, layout, input, rendering).
**How:**
- `UP<...> g_p*` globals for every manager (e.g., `g_pCompositor`, `g_pInputManager`)
- Initialized in `CCompositor::initManagers()` in staged order
- **Trade-off:** Hidden dependencies, difficult unit testing. But pragmatically necessary for a compositor.

### Decision 6: Lua Watchdog with Instruction Counting
**Why:** Prevent malformed Lua configs from hanging the compositor.
**How:**
- `lua_sethook()` with `LUA_MASKCOUNT` fires every 10k instructions
- `watchdogHook()` checks elapsed time against per-operation timeout
- Different timeouts for config reload (1500ms) vs keybind (100ms) vs event (50ms)
- **Trade-off:** Slight overhead from hook callback, but prevents compositor hangs

## 4. Three Config Systems Interaction

```
User Config File (.conf or .lua)
          │
          ▼
  Config::initConfigManager()
    ├── If .lua → uses Lua::CConfigManager
    │     - Sets up Lua state with watchdog
    │     - Loads config file via luaL_loadfile
    │     - Executes Lua → registers keybinds, values, callbacks
    │     - Lua dispatchers call via Config::Actions::* directly
    │
    └── If .conf → uses Legacy::CConfigManager
          - Parses via Hyprlang library
          - HandleRawExec/HandleBind/HandleWindowRule etc.
          - Keybinds store (dispatcher_name, arg) pairs
          - On keypress: translator()->run(name, arg)
          - translator looks up m_dispMap[name] → calls static fn
          - static fn calls wrap(Actions::someAction(...))
          - wrap() converts ActionResult → SDispatchResult
                          │
                          ▼
              Config::Actions::* (shared)
              ├── closeWindow, floatWindow, fullscreenWindow, ...
              ├── changeWorkspace, toggleSpecial, ...
              ├── moveFocus, moveInDirection, swap, ...
              ├── toggleGroup, changeGroupActive, ...
              └── setProp, pass, dpms, exit, ...

Both systems:
  - Read config values via CConfigValue<T>
  - Register values via registerPluginValue()
  - Emit IPC events via CEventManager
  - Use the same ActionState singleton
```

**The `wrap()` bridge (degree 65 god node):**
```
Legacy dispatcher fn(...)
  → calls Actions::someAction(...)
  → returns ActionResult (std::expected<SActionResult, SActionError>)
  → wrap() converts to SDispatchResult {success, error, passEvent}
  → returned to the keybind dispatcher system
```

This is the single highest-degree node because every one of the ~70 legacy dispatchers calls `wrap()`.

## 5. Error Handling Patterns

### Pattern 1: Monadic expected (Primary)
```cpp
using ActionResult = std::expected<SActionResult, SActionError>;

// Success:
return {};
// Info-level error:
return actionError("Nothing to focus", eActionErrorLevel::INFO, eActionErrorCode::NOT_FOUND);
// Warning-level error:
return actionError("Window is fullscreen", eActionErrorLevel::WARNING, eActionErrorCode::INVALID_STATE);
// Error-level error:
return actionError("Invalid arg", eActionErrorLevel::ERROR, eActionErrorCode::INVALID_ARGUMENT);
```

## 6. Security-Relevant Patterns

### 6.1. Root privilege protection
- `main.cpp` checks `NInit::isSudo()` and refuses to run as root
- `--i-am-really-stupid` flag explicitly opts in
- No dropping privileges after launch, just a blanket refusal

### 6.2. Permissions system
- `src/managers/permissions/` -- `CDynamicPermissionManager`
- Permission checks in `handlePermission()` (legacy config) and config rules
- Window rules can restrict certain operations (no_focus, no_blur, no_screen_share)

### 6.3. Screen share protection
- `no_screen_share` window rule disallows capturing a window
- `permissions/` manages screen share authorization
- `src/managers/screenshare/` -- screenshare session management

### 6.4. Lua sandboxing
- Lua watchdog prevents infinite loops / hangs
- Per-operation timeouts (50ms-1500ms)
- Limited API surface (only registered bindings exposed)
- But no true sandbox -- Lua has access to `os.execute`, `io.open` etc.
  (Config opts in by writing Lua; this is accepted risk)

### 6.5. XWayland security
- X11 override redirect windows have special handling
- X11 activation crossing protocol boundary managed carefully
- DnD bridging validates event sources

### 6.6. Socket permissions
- `CHyprCtl` creates IPC socket in `$XDG_RUNTIME_DIR/hypr/$INSTANCE/`
- XWayland lock file / socket creation (`CXWaylandServer::ensureSocketDirExists()`)

### 6.7. Token-based workspace routing
- `CTokenManager` handles `HL_INITIAL_WORKSPACE_TOKEN` env var
- Tokens can be one-shot or persistent
- Prevents workspace injection by untrusted clients

### 6.8. Signal safety
- Critical sections in input handling
- `CCompositor::m_isShuttingDown` / `m_finalRequests` prevent re-entrancy on shutdown

## 7. Bridge Nodes Deep Dive

### `wrap()` (degree 65)
- **File:** `config/legacy/DispatcherTranslator.cpp:35`
- **What:** Converts `ActionResult` -> `SDispatchResult`
- **Why it's high-degree:** EVERY legacy dispatcher (~70 functions) calls `wrap(Actions::*())` as its final step. It's the bridge between the old and new config action systems.
- **Caller or callee?** Callee (called by ~70 dispatcher functions) + called by `run()` → essentially every keyboard/mouse action passes through it.

### `actionError()` (degree 30, 29 INFERRED edges)
- **File:** `config/shared/actions/ConfigActions.hpp:22` (inline)
- **What:** Alias for `configError()` -- creates `std::unexpected<SActionError>`
- **Caller or callee?** Callee. It's a tiny factory function called by ~30+ action functions. The 29 INFERRED edges mean the graph detector identified callers that were resolved by fuzzy matching rather than AST parsing (because it's an inline in a header).
- **Pattern:** Acts as an error monad `return` value creator. Every `actionError(...)` call creates a `std::unexpected` that propagates up through `wrap()`.

### `getWorkspaceIDNameFromString()` (degree 20, bridging 9 communities)
- **File:** `helpers/MiscFunctions.cpp:126`
- **What:** Parses workspace identifiers from strings
- **Communities bridged:** Workspace history, gesture handling, dispatchers (legacy + Lua + internal), config parsing, monitor management, swipe gestures
- **Why high-degree:** Workspace identifiers appear everywhere: keybind args, config rules, IPC commands, gesture handling, window placement, workspace initialization

### `mapWindow()` (degree 24)
- **File:** `desktop/view/Window.cpp:1804`
- **What:** Called when a Wayland or X11 surface "maps" (becomes visible). This is the main function for window initialization:
  1. Sets workspace/monitor assignment
  2. Checks for `HL_INITIAL_WORKSPACE_TOKEN`
  3. Applies window rules (monitor, workspace, float, fullscreen, etc.)
  4. Registers with layout manager
  5. Handles groups (`auto_group` config)
  6. Sets up initial animation states
  7. Emits events (window open, etc.)
- **Why high-degree:** Window mapping touches ~24 subsystems: input, render, layout, workspace, config, animations, groups, focus, permissions, compositor, etc.

### `xtract()` (degree 30)
- **File:** `config/shared/actions/ConfigActions.cpp:38`
- **What:** Resolves "active window" from optional argument
  ```cpp
  static PHLWINDOW xtract(std::optional<PHLWINDOW> window) {
      return window.value_or(Desktop::focusState()->window());
  }
  ```
- **Called from:** Every action function that accepts an optional window argument (~30 functions)

### `layoutMsg()` (degree 25)
- **File:** `layout/LayoutManager.hpp:72` -> forwarded to `CAlgorithm::layoutMsg()` -> forwarded to specific algorithm
- **What:** Routes messages like "cyclenext", "orientation left", "splitratio 0.5" to the active layout algorithm
- **Why high-degree:** Each algorithm handles layout messages differently; this routing function touches all algorithms

### `idx()` (degree 17)
- **File:** `layout/algorithm/tiled/scrolling/ScrollingAlgorithm.cpp` (multiple overloads)
- **What:** Finds the index of a column or target within the scrolling layout
- **Called from:** Most scrolling layout operations (ADD, REMOVE, MOVE, RESIZE, LAYOUT_MSG, DRAG, DROP)

### `configError()` (degree 16)
- **File:** `config/shared/ConfigErrors.hpp:65`
- **What:** Factory for `std::unexpected<SConfigError>`. Base of `actionError()`.
- **Pattern:** Both config systems and the action system use it.

## 9. Graph Community Structure Interpretation

The 442 communities in the graph (318 shown) map to:

- **Large communities (1-19):** Core subsystems -- Window Actions, Monitor, Render, Layout, Config, Protocols, Input
- **Medium communities (20-50):** Individual protocol implementations (DataDevice, DragDrop, InputMethod, XDG, LayerShell)
- **Small communities (50-100):** Specific features (popups, decorations, algorithms, cursor, screencopy)
- **Tiny communities (100+):** Individual classes or functions (a few nodes each)

The high community count suggests:
1. **Strong encapsulation** -- Each protocol is isolated
2. **Many leaf nodes** -- Individual utility functions in their own communities
3. **Hub nodes bind the graph** -- `wrap()`, `actionError()`, `xtract()`, `getWorkspaceIDNameFromString()` are the bridges that keep the graph connected
