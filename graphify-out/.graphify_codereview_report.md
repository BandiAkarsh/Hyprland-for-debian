## 1. Cross-Cutting Concerns

### 1.1 Workspace Management (CONFIRMED)

Workspace lifecycle touches nearly every module:

| File | Role |
|------|------|
| `desktop/Workspace.cpp` | Core workspace object (m_workspaces) |
| `Compositor.cpp` | Creates/owns `m_workspaces`, `createNewWorkspace()`, `moveWorkspaceToMonitor()` |
| `layout/space/Space.cpp` | CSpace owns CAlgorithm, per-workspace layout state |
| `config/shared/workspace/WorkspaceRule.cpp` | Persistent/template workspace definitions |
| `managers/input/trackpad/gestures/SpecialWorkspaceGesture.cpp` | Swipe-based special workspace toggle |
| `managers/animation/DesktopAnimationManager.cpp` | Animate in/out, slide transitions, fullscreen fade |
| `desktop/state/FocusState.cpp` | Workspace changes trigger focus re-evaluation |
| `helpers/Monitor.cpp` | Monitor owns active workspace, special workspace |
| `Desktop::history::WorkspaceHistoryTracker` | Forward/back navigation |
| `config/shared/workspace/WorkspaceRuleManager.cpp` | Applies persistent workspace rules |

**Relationship**: Control flow + shared state (the workspace objects are passed around by SP/WP).
**Explicit?** Implicit. There's no single "workspace lifecycle" orchestrator; it emerges from CCompositor's methods and the signal system.

### 1.2 Focus System (CONFIRMED)

The focus system is a cross-cutting state machine:

| File | Role |
|------|------|
| `desktop/state/FocusState.hpp` | Singleton-like CFocusState holds m_focusWindow/m_focusSurface/m_focusMonitor |
| `desktop/state/FocusState.cpp` | `fullWindowFocus()`, `rawWindowFocus()`, `rawSurfaceFocus()` |
| `managers/input/InputManager.cpp` | `refocus()`, mouse-move-driven focus decisions |
| `managers/KeybindManager.cpp` | `focusWindow dispatcher`, `focusMonitor dispatcher` |
| `config/shared/actions/ConfigActions.cpp` | `focus()`, `focusCurrentOrLast()`, `focusUrgentOrLast()` |
| `layout/algorithm/tiled/*.cpp` | `focusTargetUpdate()` in tiled algorithms |
| `Compositor.cpp` | `getForceFocus()`, window open/unmap refocus |

**Relationship**: Global shared state (CFocusState) + signals emitted on change. ~15+ eFocusReason values document WHY focus changed.
**Explicit?** Partially. The state is explicitly centralized in CFocusState, but the triggering paths are distributed.

### 1.3 Animation Lifecycle (CONFIRMED)

Animation lifecycle spans config -> per-window state -> render loop:

```
Config file -> CAnimationPropertyConfig
    |
CHyprAnimationManager::createAnimation() -> CAnimatedVariable<T>
    | (on value changes)
scheduleTick() -> frameTick() -> tick()
    |
Render loop reads: getGoal(), getValue() on animated vars
    |
CDesktopAnimationManager handles visual transitions (popin, slide, gnome)
```

**Key files**: `helpers/AnimatedVariable.hpp` (templated), `managers/animation/AnimationManager.hpp`, `managers/animation/DesktopAnimationManager.hpp`, `render/Renderer.cpp` (reads animated values per frame).

**Relationship**: Data flow (animated values -> damage -> render).
**Explicit?** Yes -- the templated CAnimatedVariable system is well-documented in code.

### 1.4 Damage Tracking (CONFIRMED)

Damage is a cross-cutting concern that propagates from input/re-layout -> render:

```
Window moved/resized -> damageWindow() / damageBox() / damageRegion()
    |
DamageRing accumulates
    |
On frame: CMonitorState::commit() -> renderMonitor() -> CRenderPass::render()
    |
CRegion damage used for scissor-test rendering
```

**Key files**: `helpers/DamageRing.cpp`, `render/Renderer.cpp` (`damageWindow`, `damageBox`, `damageRegion`), `helpers/Monitor.cpp` (per-monitor damage state).

**Explicit?** Explicit -- damage is a first-class tracked concept in the rendering path.

## 2. Design Patterns

### 2.1 Singleton via Global Inline Pointers (CONFIRMED)

Every major manager uses the pattern:
```cpp
inline UP<CCompositor> g_pCompositor;
inline UP<CPluginSystem> g_pPluginSystem;
inline UP<CKeybindManager> g_pKeybindManager;
inline UP<CEventLoopManager> g_pEventLoopManager;
inline UP<CHyprAnimationManager> g_pAnimationManager;
inline UP<CDesktopAnimationManager> g_pDesktopAnimationManager;
inline UP<Render::IHyprRenderer> g_pHyprRenderer;
inline UP<CEventManager> g_pEventManager;
inline UP<CProtocolManager> g_pProtocolManager;
inline UP<Layout::CLayoutManager> g_layoutManager;
```

**21+ singletons** across the codebase. This is an implicit architectural pattern -- there is no Singleton base class, just convention.

**Explicit?** Implicit. Not formalized, just consistently done.

### 2.2 Strategy Pattern: Layout Algorithms (CONFIRMED)

```
CAlgorithm (facade/delegate)
  +-- ITiledAlgorithm (interface)
  |   +-- CMasterAlgorithm (3-col layout, master/stack)
  |   +-- CMonocleAlgorithm (fullscreen each window)
  +-- IFloatingAlgorithm (interface)
      +-- CFloatingAlgorithm
```

Each `CSpace` (per-workspace) holds a `UP<CAlgorithm>`. Algorithms are pluggable from plugins via `HyprlandAPI::addTiledAlgo()`. Layout messages parsed with `layoutMsg()` dispatch to algorithm-specific commands.

**Key files**: `layout/algorithm/Algorithm.hpp`, `layout/algorithm/tiled/TiledAlgorithm.hpp`, `layout/algorithm/floating/FloatingAlgorithm.hpp`, `layout/LayoutManager.hpp`.

**Explicit?** Explicit -- well-defined interfaces, clear strategy pattern.

### 2.3 Observer Pattern via CHyprSignalListener (CONFIRMED)

The entire event system is built on `hyprutils/signal/Signal.hpp`:

Used for:
- Window open/close/map/unmap events (to Lua event handler)
- Monitor mode changes (to ProtocolManager)
- Session lock/unlock
- Configuration reload triggers
- Focus changes

The Lua event handler (`CLuaEventHandler`) registers C++ signal listeners and translates them into Lua function invocations.

**Key files**: `helpers/signal/Signal.hpp` (re-export from hyprutils), `config/lua/LuaEventHandler.hpp`, `managers/ProtocolManager.hpp`.

**Explicit?** Explicit -- the signal system is a well-documented abstraction.

### 2.4 Command Pattern: Keybind Dispatchers + Config Actions (CONFIRMED)

Two parallel command dispatch systems:

**Legacy dispatchers**: `CKeybindManager::m_dispatchers` -- `std::unordered_map<std::string, std::function<SDispatchResult(std::string)>>`. String-named handlers (e.g., "exec", "movetoworkspace"). Plugins can register via `addDispatcherV2`.

**Config Actions**: `Config::Actions` namespace -- stateless functions returning `std::expected<SActionResult, SActionError>`. The new composable action system.

**Key files**: `managers/KeybindManager.hpp`, `config/shared/actions/ConfigActions.hpp`.

**Explicit?** Explicit -- both patterns are clearly defined.

### 2.5 Template-Method Pattern: Render Pass Elements (CONFIRMED)

```cpp
class IPassElement {
    virtual std::vector<UP<IPassElement>> draw() = 0;
    virtual bool needsLiveBlur() = 0;
    virtual const char* passName() = 0;
    virtual ePassElementType type() = 0;
};
```

11 concrete implementations: CBorderPassElement, CClearPassElement, CFramebufferElement, CPreBlurElement, CRectPassElement, CRendererHintsPassElement, CShadowPassElement, CSurfacePassElement, CTexPassElement, CTextureMatteElement, CInnerGlowPassElement.

They're collected by `CRenderPass::add()` and rendered in `CRenderPass::render()` with damage-based simplification and occlusion culling.

**Key files**: `render/pass/PassElement.hpp`, `render/pass/Pass.hpp`, `render/pass/*Element.hpp`.

**Explicit?** Explicit -- clearly defined interface hierarchy.

## 3. Error Handling Architecture (CONFIRMED)

Hyprland uses `std::expected<T, Error>` (C++23) pervasively:

```
Config::ErrorResult = std::expected<void, SConfigError>
Config::Actions::ActionResult = std::expected<SActionResult, SActionError>
```

**Error structure**:
```cpp
struct SConfigError {
    std::string message;
    eConfigErrorLevel level;    // SILENT, INFO, WARNING, ERROR
    eConfigErrorCode code;      // INVALID_ARGUMENT, NOT_FOUND, NO_TARGET, etc.
};
```

**Helper functions**:
- `configError(msg, level, code)` -> `std::unexpected<SConfigError>` (ConfigErrors.hpp)
- `actionError(msg, level, code)` -> aliases configError for action system (ConfigActions.hpp)
- `layoutMsg(string_view)` -> returns `Config::ErrorResult` (LayoutManager.hpp)

**Propagation pattern**: Errors bubble up through callsites with `std::expected`. The graph report shows `actionError()` with 30 edges -- it's one of the most connected nodes. `configError()` has 16 edges. Both are **god nodes** in the graph.

**Key files**: `config/shared/ConfigErrors.hpp`, `config/shared/actions/ConfigActions.hpp`, `layout/LayoutManager.hpp`.

**Note**: Not all subsystems use this pattern. The Lua subsystem has `addError()` / `addEvalIssue()` (collect errors in a vector), and there's also `exitWithError()` for fatal crashes (community 99 in graph).

**Explicit?** Explicit -- well-defined error types and propagation pattern.

## 4. State Management Architecture (CONFIRMED)

### 4.1 Explicit Singleton Managers

Each manager class owns its state internally. Access is via the global singleton pointer:

| Singleton | State Owned |
|-----------|-------------|
| CCompositor | m_monitors, m_windows, m_layers, m_workspaces, m_wlDisplay |
| CInputManager | m_keyboards, m_pointers, m_touches, m_hids, m_constraints, m_forcedFocus |
| CKeybindManager | m_keybinds, m_dispatchers, m_pressedKeys, m_activeKeybinds |
| CPluginSystem | m_loadedPlugins |
| Layout::CLayoutManager | m_dragStateController |

### 4.2 State Objects with Weak-Pointer Patterns

- `CFocusState` -- standalone state object, accessed via `focusState()` (returns `SP<CFocusState>`)
- `CFloatStateCache` -- remembers floating window sizes, accessed via `floatState()`
- `Desktop::history::CWindowHistoryTracker` -- navigation history
- `Desktop::history::CWorkspaceHistoryTracker` -- workspace navigation

### 4.3 Hybrid Smart Pointer System

The codebase uses `PHLWINDOW`/`PHLWINDOWREF`, `PHLMONITOR`/`PHLMONITORREF`, etc. -- typed aliases for `SP<T>`/`WP<T>`. The REF variants (weak pointers) are used for:
- Cached/lingering references that must not keep objects alive
- Window decorations holding back-pointers
- Animation context references

### 4.4 Threading Model: Single-threaded Event Loop (CONFIRMED)

The compositor runs on a single `wl_event_loop`. There is:
- **No threading in the main render/input loop**
- `CEventLoopManager::doLater()` -- defers work to the main loop via idle events
- `CEventLoopManager::doLaterLock()` -- same but with a scope guard
- `CEventLoopManager::doOnReadable()` -- async FD monitoring on main loop
- Hyprutils::OS::CFileDescriptor -- RAII wrapper for fds used in event loop

The only true async is:
- `render/AsyncResourceGatherer.hpp` -- background loading (likely thread pool)
- `CFunctionHook` -- raw assembly manipulation (not async per se, but dangerous)

**Explicit?** Explicit -- the event loop pattern is clearly defined in EventLoopManager.

## 5. Extension Points (CONFIRMED)

### 5.1 Plugin System (`plugins/`)

The plugin API (`PluginAPI.hpp`) provides a C-ABI surface for dynamically loaded `.so` files:

| API Function | Purpose |
|-------------|---------|
| `addTiledAlgo` / `addFloatingAlgo` | Register new layout algorithms |
| `addConfigValueV2` | Add plugin configuration values (plugin: namespace) |
| `createFunctionHook` | Create raw function hooks (assembly trampolines) |
| `addDispatcherV2` | Register keybind dispatchers |
| `registerHyprCtlCommand` | Add custom hyprctl commands |
| `addWindowDecoration` | Add visual decorations to windows |
| `addNotificationV2` | Show notifications |
| `addLuaFunction` | Register Lua-callable C functions |
| `findFunctionsByName` | Runtime symbol lookup for hooking |

Function hooks (`CFunctionHook`) are a **raw assembly trampoline system** -- they copy original bytes, overwrite with a jump to the hook, and provide the original via `m_original`. This is explicitly marked as unstable.

### 5.2 Lua Scripting (`config/lua/`)

Lua is a first-class configuration language:

```
Config::Lua::CConfigManager {
    lua_State* m_lua;         // Lua VM state
    CLuaEventHandler* m_eventHandler;  // hl.on() subscription
    std::vector<SLuaTimer> m_luaTimers; // hl.timer()
    std::vector<Layouts::SLuaLayoutProvider> m_luaLayoutProviders;
    // ... plugin Lua functions, config values, etc.
}
```

**Capabilities**:
- `hl.on(event, callback)` -- event subscriptions via CLuaEventHandler
- `hl.timer(delay, callback)` -- timer callbacks
- Lua layout providers (register custom layouts in Lua)
- Plugin Lua functions registered into `hl.plugin.<namespace>.<name>`
- Watchdog system (instruction counting + timeouts) to prevent runaway scripts

### 5.3 In-Process Extension via Signals

The `CHyprSignalListener` system allows internal modules to observe events. The Lua event handler bridges this to user scripts.

## 6. Configuration Flow (CONFIRMED)

```
hyprland.conf (file on disk)
    |
    v
ConfigManager (Legacy:: or Lua:: via IConfigManager interface)
    |  init(), reload(), verify()
    |
    v
Config Values (SP<Config::Values::IValue>)
    |  getDeviceInt(), getConfigValue(), etc.
    |
    v
Consumer Modules (poll values on access / register listeners)
    |
    +-- InputManager (keyboard layout, pointer settings)
    +-- MonitorRuleManager (monitor rules -> SMonitorRule)
    +-- KeybindManager (keybinds -> m_keybinds, m_dispatchers)
    +-- RuleEngine (window rules -> rule matching)
    +-- Layout system (layout algorithm selection)
    +-- AnimationManager (animation config)
```

**Config change triggers**:
1. Watchdog/inotify detects file change
2. `ConfigManager::reload()` called
3. Values re-parsed
4. Effects propagate through polling (values read on use) or signals

## 7. Thread Safety Assessment (CONFIRMED)

| Pattern | Where | Thread-safe? |
|---------|-------|-------------|
| wl_event_loop single-thread | Main loop | N/A (single-threaded by design) |
| `doLater()` deferred execution | EventLoopManager | Yes (main-loop dispatch) |
| `CEventLoopTimer` | EventLoopManager | Single-thread (main loop timerfd) |
| `CSyncTimeline` / `SyncReleaser` | helpers/sync/ | DRM sync objects (kernel-level) |
| `CFunctionHook` assembly patches | plugins/HookSystem | **NOT THREAD SAFE** |
| `AsyncResourceGatherer` | render/ | Background thread, main-loop result delivery |
